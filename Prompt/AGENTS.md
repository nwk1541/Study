# Project Agent Instructions

All responses must be in Korean (한국어).

## 작업 권한과 검증(Autonomy and Validation)

- 답변, 설명, 검토, 진단, 계획 요청에서는 관련 자료를 조사하고 결과만 보고한다. 구현은 명시적으로 요청된 경우에만 한다.
- 변경, 구현, 수정 요청에서는 범위 내 로컬 변경과 관련된 비파괴적 검증까지 별도 승인 없이 진행한다.
- 기존 미커밋 변경을 임의로 덮어쓰거나 되돌리지 않는다. 별도 요청이 없는 되돌리기는 이번 작업에서 만든 변경으로 제한한다.
- 사용자가 이미 명시적으로 요청한 작업을 제외하고, 외부 서비스 쓰기, 원격 저장소 변경, 사용자 데이터·프로젝트 자산의 파괴적 삭제, 패키지 추가·삭제·버전 변경, 비용 발생 또는 목표를 벗어나는 실질적인 범위 확장은 먼저 확인한다.
- 변경 후에는 가능한 범위에서 가장 관련성 높은 컴파일, 테스트 또는 정적 분석을 실행한다. 실행 검증이 불가능하면 변경된 코드 경로를 정적으로 검토하고 그 이유와 한계를 명시한다.
- 단, Unity Editor 및 관련 실행 도구(Batch Mode, Test Runner), Unity 프로젝트의 `.sln`/`.csproj`에 대한 `dotnet build` 또는 MSBuild는 사용자가 명시적으로 요청한 경우에만 실행한다.
- 결과 보고에서는 정적 확인과 실제 컴파일·테스트·런타임 검증을 구분한다.

## 코딩 가이드라인(Coding Guidelines)

**트레이드오프(Tradeoff):** 정확성과 안정성을 우선하되, 유지보수성, 성능, 구현 속도를 작업의 성격, 위험도와 규모에 맞게 균형 있게 판단한다.

### 1. 코딩 전에 생각하기(Think Before Coding)

- 구현 방향, 권한, 변경 범위에 실질적인 영향을 주는 불확실성은 먼저 코드베이스를 조사하여 해소한다. 그래도 중요한 판단이 남으면 무엇이 불명확한지 설명하고 최소한의 질문으로 확인한다. 그 외에는 필요한 가정을 명시하고 진행한다.
- 설계 선택지가 결과에 실질적인 영향을 주면 주요 대안을 비교하고 더 단순한 접근법도 함께 검토한다. 사용자가 지정한 방향보다 명확히 나은 대안이 있고 차이가 중요하면 이유와 함께 제안하되, 사용자 요구를 임의로 대체하지 않는다.

### 2. 단순함 우선(Simplicity First)

- 요청을 해결하는 가장 작은 일관된 설계를 구현하고, 기존 프로젝트의 스타일과 컨벤션을 따른다.
- 요청되지 않은 기능, 추측성 코드, 불필요한 추상화·인터페이스·제네릭 클래스·설정 가능성을 추가하지 않는다. 프로젝트의 계약, 타입 또는 상태 불변식상 발생할 수 없다고 확인된 시나리오를 위한 방어 코드도 추가하지 않는다.
- 요청과 무관한 리팩터링이나 코드·주석·포맷팅 변경은 하지 않는다. 관련 없는 데드 코드나 버그는 보고만 한다.
- 신규 기능이나 변경을 일관되게 구현하고 중복된 책임, 우회 분기 또는 병렬 구현을 방지하는 데 필요한 관련 내부 구조는 수정·통합·대체 또는 제거할 수 있다. 이번 변경으로 불필요해진 import, 변수, 함수, 분기와 이전 구현 경로는 함께 정리한다.
- 호환성 요구가 없는 경우 기존 구현을 보존하기 위한 새 필드, 함수, 래퍼, 플래그 또는 오버로드를 누적하지 않는다.

### 3. 목표 기반 실행과 계획(Goal-Driven Execution)

- 여러 파일·시스템에 걸치거나 영향도가 큰 작업은 구현 전에 짧은 계획(단계 → 검증 방법)을 세운다. 단순하고 국소적인 변경은 바로 진행한다.
- 작업을 검증 가능한 목표로 바꾼다. 예: 버그 수정은 재현 조건과 수정 후 확인 방법을 먼저 정의한다.
- 변경 전후의 핵심 조건, 분기, 호출 대상과 상태 변화를 확인하고 필요한 검증에 반영한다.

### 4. 영향도 분석(Impact Analysis)

- 공개 API, 공통 유틸리티, 시그니처, 반환값 또는 핵심 상태를 변경할 때는 관련 호출자와 참조를 필요한 범위까지 먼저 조사한다.
- 변경해야 할 호출부와 구현체가 명확하고 변경 방식이 일관되며 위 작업 권한 지침에서 사전 확인이 필요한 작업에 해당하지 않으면 함께 수정한다. 호환성이 실제로 필요한 경우에만 기존 시그니처 유지, 어댑터 또는 오버로드를 고려한다.
- 작업 중 요청이나 기존 승인 범위를 벗어나는 영향이 확인되면, 적용 전에 영향과 대안을 설명하고 확인한다.

## File Encoding
- 기존 파일은 인코딩, BOM 유무, 줄바꿈 형식을 유지한다. 기존 파일은 부분 수정하고, 전체를 덮어쓰는 것은 새 파일이나 전면 교체에만 사용한다.
- 새 텍스트 파일은 기본적으로 UTF-8 with BOM으로 작성하되, 파일 형식이나 사용 도구에 별도 요구사항이 있으면 이를 우선한다.

## Coding Conventions
- private 필드는 `_camelCase`를 사용한다. 예: `_videoPlayer`, `_isLoading`
- enum은 주로 `E` 접두사를 사용한다. 예: `EBattlePopupType`, `EAppState`
- 상수(`const`)는 `UPPER_SNAKE_CASE`를 사용한다. 예: `CATEGORY_NAME`, `KEY_SORT_OPTION`
- 일반 `bool` 조건은 `== true` / `== false` 비교 대신 `if (condition)` / `if (!condition)` 형태를 사용한다. `bool?` 또는 null 조건부 접근(`?.`) 결과는 null의 의미를 보존하도록 비교한다.
- 메서드의 파라미터나 호출 인자 목록이 길더라도 임의로 개행하지 않고 한 줄로 유지한다.

## 작업 도구 및 사용 기준
- 탐색은 기본적으로 `rg`를 사용한다. C# 코드 구조를 구분하느라 정규식 작성이나 결과 검토가 복잡해질 때는 `ast-grep`을 사용하며, 가능한 경우 대상 범위를 먼저 좁힌다.
- sqlite3: `Tools/sqlite-tools-win-x64-3530200/sqlite3.exe`
- Python도 사용할 수 있으며, `rg`, `ast-grep`, PowerShell, sqlite3 등 다른 도구보다 작업을 효율적으로 처리할 수 있을 때 선택한다.
- PowerShell에서 한글이 포함된 텍스트 파일을 읽을 때는 `Get-Content -Encoding UTF8`을 사용한다.
