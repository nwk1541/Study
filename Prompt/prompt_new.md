## 코딩 가이드라인(Coding Guidelines)

**트레이드오프(Tradeoff):** 정확성과 안정성을 우선하되, 유지보수성, 성능, 구현 속도를 작업의 성격, 위험도와 규모에 맞게 균형 있게 판단한다.

### 1. 코딩 전에 생각하기(Think Before Coding)

**추측을 숨기지 말고, 중요한 트레이드오프를 드러낸다.**

- 구현 방향, 권한, 변경 범위에 실질적인 영향을 주는 불확실성이 있으면 먼저 코드베이스와 관련 자료를 조사하여 해소한다. 그래도 중요한 판단이 남으면 무엇이 불명확한지 설명하고 최소한의 질문으로 확인한다.
- 그 외에는 필요한 가정을 명시하고 안전한 범위에서 진행한다.
- 여러 설계 선택지가 결과에 실질적인 영향을 주면 주요 대안을 비교한다. 더 단순한 접근법이 있으면 함께 검토한다.
- 사용자가 지정한 방향보다 설계적으로 명확히 나은 대안이 있고 그 차이가 중요하면 이유와 함께 제안하되, 사용자 요구를 임의로 대체하지 않는다.

### 2. 단순함 우선(Simplicity First)

**요청을 해결하는 가장 작은 일관된 설계를 구현하고, 변경 범위를 관련된 코드로 제한한다.**

- 명시적으로 요청되지 않은 기능, 추측성 코드, 불필요한 추상화·인터페이스·제네릭 클래스·설정 가능성을 추가하지 않는다.
- 정상 동작하는 관련 없는 코드는 인접했다는 이유만으로 리팩터링하거나 코드·주석·포맷팅을 임의로 변경하지 않는다.
- 신규 기능이나 변경을 일관되게 구현하고 중복된 책임, 우회 분기 또는 병렬 구현을 방지하는 데 필요한 관련 내부 구조는 수정·통합·대체 또는 제거할 수 있다.
- 기존 프로젝트의 스타일과 컨벤션을 따른다.
- 이번 변경으로 불필요해진 import, 변수, 함수, 분기와 이전 구현 경로는 함께 정리한다.
- 호환성 요구가 없는 경우 기존 구현을 보존하기 위한 새 필드, 함수, 래퍼, 플래그 또는 오버로드를 누적하지 않는다.
- 기존의 관련 없는 데드 코드나 버그는 언급만 하고 요청 없이 수정하지 않는다.
- 모든 변경은 사용자의 구체적인 요청을 직접 지원하거나 그 요청을 일관되게 구현하는 데 필요해야 한다.
- 프로젝트의 계약, 타입 또는 상태 불변식상 발생할 수 없다고 확인된 시나리오를 위한 방어 코드나 추측성 분기를 추가하지 않는다.
- 변경 범위 안에서 같은 동작을 더 단순하게 표현할 수 있다면 단순한 구현을 우선한다.

### 3. 권한 경계와 검증(Autonomy and Validation)

- 답변, 설명, 검토, 진단, 계획 요청에서는 관련 자료를 조사하고 결과만 보고한다. 구현은 명시적으로 요청된 경우에만 한다.
- 변경, 구현, 수정 요청에서는 범위 내 로컬 변경과 관련된 비파괴적 검증까지 별도 승인 없이 진행한다.
- 사용자가 이미 명시적으로 요청한 작업을 제외하고, 외부 서비스 쓰기, 원격 저장소 변경, 사용자 데이터·프로젝트 자산의 파괴적 삭제, 패키지 추가·삭제·버전 변경, 비용 발생 또는 목표를 벗어나는 실질적인 범위 확장은 먼저 확인한다.
- 변경 후에는 가능한 범위에서 가장 관련성 높은 컴파일, 테스트 또는 정적 분석을 실행한다. 실행 검증이 불가능하면 변경된 코드 경로를 정적으로 검토하고 그 이유와 한계를 명시한다.

### 4. 목표 기반 실행과 계획(Goal-Driven Execution)

**여러 파일·시스템에 걸치거나 영향도가 큰 작업은 구현 전에 짧은 계획을 세운다. 단순하고 국소적인 변경은 별도 계획 없이 바로 진행한다.**

- 작업을 검증 가능한 목표로 바꾼다. 예: 유효성 검사는 잘못된 입력 테스트로, 버그 수정은 재현 방법과 수정 검증으로 정의한다.
- 계획이 필요한 경우 필요한 단계만 포함하고 각 단계에 검증 방법을 연결한다.

  1. [단계] → 검증: [확인 방법]
  2. [단계] → 검증: [확인 방법]

- 변경 전후의 핵심 조건, 분기, 호출 대상과 상태 변화를 확인하고 필요한 검증에 반영한다.
- Unity Editor 및 관련 실행 도구(Batch Mode, Test Runner)는 사용자가 명시적으로 요청한 경우에만 실행한다.

### 5. 영향도 분석(Impact Analysis)

**공개 API, 공통 유틸리티, 시그니처, 반환값 또는 핵심 상태를 변경할 때 실제 영향 범위를 먼저 확인한다.**

- 관련 호출자와 참조를 필요한 범위까지 조사하고 예상되는 호환성 영향을 확인한다.
- 호출부 변경이 필요 없는 내부 구현 변경은 필요한 범위에서 진행한다.
- 변경해야 할 호출부와 구현체가 명확하고 변경 방식이 일관되며 승인 대상에 해당하지 않는 경우에는 함께 수정한다.
- 호환성이 실제로 필요한 경우에만 기존 시그니처 유지, 어댑터 또는 오버로드를 고려한다.
- 사용자가 처음부터 광범위한 변경의 대상과 범위를 명시한 경우에는 그 요청을 해당 범위에 대한 승인으로 간주한다.
- 그 외에 작업 중 20개를 초과하는 기존 파일·자산을 수정해야 하는 경우에는, 변경이 기계적이고 일관적이더라도 먼저 예상 변경 범위와 영향을 보고하고 사용자 승인 전에는 적용하지 않는다.
- 개수와 관계없이 공개 계약의 호환성을 깨거나, 직렬화·저장 데이터 마이그레이션이 필요하거나, 여러 독립 시스템으로 변경 범위가 실질적으로 확대되는 경우에도 영향과 대안을 보고하고 사용자 승인 전에는 적용하지 않는다.
